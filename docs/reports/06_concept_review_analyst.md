## 1. 모순 (Contradictions) — 문서 내 상충 주장

### C1 — 정의 1 "외부 서버 운영 안 함" vs 실제 HTTP 서버 운영

[사실] 05 §1.1 정의 1은 **"독립형 브라우저 도구다. MCP가 아니다. 외부 서버를 운영하지 않는다."**(`05:51`)라고 규정한다. 그러나 동일 문서 §3.2.3은 `bridge_server.py`를 `ThreadingHTTPServer` 기반 HTTP 서버(`bridge_server.py:114-128`, bind `127.0.0.1:10899`)로 보존 대상에 올린다(`05:167`). §6.1 Q1(a)도 "핸드오프 수신은 Python `HandoffReceiver`(10899)가 중개하는 것이 자연스러움"을 명시한다(`05:330`).

[반대증거] 즉 05는 "서버 운영 안 함"을 선언하면서, 동시에 로컬 루프백 HTTP 서버를 핵심 구성요소로 유지한다. "외부 서버"의 정의(원격/클라우드 백엔드인가, 로컬 데몬/HTTP 리스너인가)가 문서 어디에도 정의되지 않아, 정의 1의 경계가 모호하다.

[권고] 정의 1을 **"원격/클라우드 백엔드 서버는 운영하지 않는다(로컬 루프백 브리지 10899는 예외)"**로 스코프를 한정하고, "외부 서버"라는 모호어를 제거하라. 모호한 채로 두면 "이 컴포넌트가 허용되는가"라는 리부트 논쟁이 재현된다(05 스스로 막으려는 패턴). 이 모호성은 정의 1이 MCP(원격 프로토콜 노출)와 로컬 브리지(로컬 리스너)를 구분하지 못한 데서 온다.

### C2 — 정의 2·정보경로 1 "에이전트가 9222에 직접 붙음(주경로)" 확정 vs Q1 "미결" 개방

[사실] 05 §1.1 정의 2는 **"에이전트(Agent): CDP / Playwright로 브라우저를 제어한다. 구체적으로 외부 에이전트가 9222 포트(CDP 진입점)에 붙어 실제 Chrome 세션을 조작한다."**(`05:56-58`)라고 확정한다. §2.1 정보경로 1도 **"주 경로는 인간이 로그인한 실제 Chrome 프로파일을 에이전트가 CDP로 이어받는 것"**(`05:102`)으로 확정한다.

[반대증거] 그런데 §6.1 Q1은 "외부 에이전트가 CDP 포트(9222)에 **직접** 붙는가, Python(`agent_iface`)이 **중개**하는가?"를 **미결 과제**로 남긴다(`05:327-331`). 정의 2와 정보경로 1이 이미 "직접 붙음 = 주경로"로 답했는데, Q1이 같은 사안을 "열려 있다"고 중복 개방하는 것은 자기모순이다. 더욱이 §6.5 장단점 표는 "(c) 병존(용도별) … v2.0 권고안"(`05:362`)이라며 사실상 답을 내놓고도 Q1 본문은 "결정 필요"로 방치한다.

[권고] Q1의 "직접 vs 중개" 프레임 자체를 닫고, 열려 있는 실질 하위문제만 남겨라: (1) 9222 직접 제어 경로는 확정, (2) 10899는 핸드오프 수신 전용으로 경계 고정. 혼선을 줄이려면 Q1을 "(a)직접 주력+(b)10899는 핸드오프 전용"으로 조기 결론 내고 버전 bump하라.

### C3 — §5.4 완료기준 "E2E 런타임 CDP 제어" 포함 vs Q4 "게이트 포함 여부 미결" 개방

[사실] 05 §5.4 완료기준 3항은 **"E2E: 실제 Chrome 기동 → 익스텐션 → 핸드오프 수신 → 외부 에이전트 CDP 제어(§6.4 한계였던 런타임 연결 실제 성공)"**(`05:299`)를 명시한다. 즉 재작성 완료 게이트에 이미 포함됐다.

[반대증거] 그러나 §6.4 Q4는 "이 E2E를 (a)재작성 완료 게이트에 포함, (b)별도 후속 과제로 분리 중 탭일"을 **미결**로 남긴다(`05:346-350`). §5.4가 이미 (a)를 채택했으므로 Q4의 "개방" 프레임은 §5.4와 충돌한다. 같은 문서가 한쪽에선 "완료기준"으로, 다른 쪽에선 "미결"로 동일 항목을 다루는 것은 내적 불일치다.

[권고] Q4를 §5.4와 정합하도록 "(a)게이트 포함(이미 §5.4 반영)"으로 조기 결론 내고, 실제 `page.goto`/클릭 E2E 스모크를 게이트 스크립트로 구체화하라.

### C4 — 정의 3 제목 "도구는 제어 프로토콜만" vs 본문 열거 항목(제어 외 기능)

[사실] 05 §1.1 정의 3 제목은 **"도구는 제어 프로토콜만 제공한다"**(`05:62`)이나, 같은 항목 본문은 도구가 하는 일로 **"세션 기동, DOM/스크린샷/클립보드 추출, 핸드오프 수신, CDP 제어 인터페이스 노출"**(`05:63`)을 모두 나열한다. "제어 프로토콜만"이라는 '만(only)'과, 그 아래 나열된 비(非)제어 기능군(추출·수신·기동)이 자기충돌한다.

[사실 — 위임 요청 예시의 위양성 해명] 작업 지시서는 모순 예시로 **"도구는 제어 프로토콜만" vs 실제 `cdp_bridge.py`가 제어 수행**을 들었다. 이를 검증한 결과 **이는 모순이 아니다.** 정의 3 본문이 "CDP 제어 인터페이스 노출"을 도구 책임으로 명시(`05:63`)하고, 실제 `cdp_bridge.py:82`의 `page.goto`는 그 제어 책임의 이행이므로 정의 3과 정합하다. 작업 지시서 예시는 오히려 **위양성(false positive)**이며, 본 Analyst는 증거 기반으로 "모순 아님"을 확인한다.

[반대증거 — 진짜 문제] 다만 실제 문제는别的 곳에 있다. `cdp_bridge.control()`이 실제 네비게이션(행동)까지 수행하므로, 정의 3이 구분하려는 경계("제공한다(인터페이스)" vs "수행한다(실행)")가 코드에서 흐릿하다. 게다가 §3.2.4는 이 `control()`을 "MVP 더미 제어"(`cdp_bridge.py` docstring `:69`)로 치부하는데, §1.1 정의 3은 "도구가 하는 일"에 "CDP 제어 인터페이스 노출"을 넣어 정합시켰다. 즉 정의 3은 표면적으로는 맞지만, "제어는 도구가 수행하는가 아니면 외부 에이전트가 수행하는가"라는 경계가 `cdp_bridge`(도구가 수행)와 정의 3의 "두뇌만 외부" 사이에서 불분명하다.

[권고] 정의 3 제목의 '만'을 삭제하고 **"도구는 제어 평면(control plane)이며, 두뇌(LLM/Vision)는 외부에 있다"**로 재규정하라. "제어 수행 여부"가 아니라 "추론/비전 유무"가 본질 경계이므로 그렇게 둬야 리부트 방지 의도(§0.1)와 맞다. `cdp_bridge.control()`의 goto 실행은 "도구가 제어를 수행한다"는 명시적 문구로 정의 3 본문에 편입하라.

## 2. 누락 (Omissions) — 빠진 책임 경계

### O1 — 스크린샷 폴백 트리거 판단 주체 미명시 + capture 체인 선택 주체 부재

[사실] 05 §2.3은 "DOM 실패 판단 시 스크린샷 캡처"만 규정하고 **판단 주체를 §6 개방질문(Q2)으로 남긴다**(`05:118`). §2.5는 **"capture 계층은 DOM → 폴백(PNG) → 대안(클립보드) 순의 전략 체인으로 동작"**(`05:136`)한다고 하나, 이 체인에서 **"다음 단계로 넘길지 결정하는 주체"**가 익스텐션/CS인지, Python context인지, 외부 에이전트인지 어디에도 정의되지 않는다.

[반대증거] 05 §3.1의 5모듈(session/capture/bridge/control/agent_iface) 중 어느 곳에도 "체인 선택 권한"이 배정되지 않는다. `capture`는 `CaptureStrategy`로 전략을 묶되(§3.2.2), **컨텍스트가 전략을 고르는 주체**는 미정의다. 또한 §2.4 클립보드 경로는 "OS 클립보드 읽기 권한 하에"(`05:124`)라고만 해두어, 권한 획득 책임 주체(익스텐션인가 Python인가)조차 불명확하다.

[권고] Q2 결론과 별도로, §2.5 체인의 "판단 주체"를 모듈 경계에 명시하라. 예: 익스텐션은 "DOM 파싱 가능 여부"만 1차 플래그하고, 체인 전환 결정은 외부 에이전트(정의 3 일치)가 한다. 책임 주체 누락은 05가 경고하는 "개념 단계에서 결론 안 난 채 구현으로 넘어간" 전형적 리부트 원인(§0.1)이다.

### O2 — R5(분할 화면 협업 UI) 완전 생략

[사실] `IDEA.md` §3 R5는 **"분할 화면 협업: 사용자와 에이전트가 분할 화면으로 같은 세션을 함께 볼 수 있다"**(`IDEA.md:16-17`)를 핵심 요구사항으로 둔다. `IDEA.md` §4도 "실시간 분할 화면 협업 UI"를 후속 범위로 명시한다. `.hermes.md` 개요(`7행`)와 `IDEA.md` §1 목적(`4행`)도 "함께 볼 수 있는" 협업 환경을 강조한다.

[반대증거] 05 본문(§1 정체성 ~ §5 재작성) 어디에도 R5/협업 UI/분할 화면 언급이 없다. 05 부록 A는 `IDEA.md` §3 R1~R5를 증거로 인용(`05:393`)하면서도, 정작 R5는 개념 재정의에서 정의하지 않는다. "무엇인가"를 규정한다는 05의 목적(§0 배경)에 비추어 핵심 요구사항 하나가 사라진 것은 개념 공백이다.

[권고] R5를 §1 정체성(이중 사용자 모델의 "함께 보기" 축) 또는 §2 정보경로에 명시적으로 편입(비목표화 금지)하거나, "v1 범위 외 후속"으로 문서상 위계를 정하라. 편입 방식을 정하지 않으면 추후 "협업 UI는 언제 했나"라는 리부트 토론이 재현된다.

### O3 — R4 "저장(persistence)" 책임 주체 누락

[사실] `IDEA.md` R4는 **"DOM 추출·저장"**(`IDEA.md:16`)이며, 05 §2.2도 "영속 저장은 미구현"을 `[반대증거]`로 인정한다(`05:111`). 그러나 05 §3.1의 5모듈 중 **영속 저장을 책임지는 모듈이 없다**(session=기동/포트, capture=추출, bridge=수신, control=제어, agent_iface=연결점).

[반대증거] 05 §3.2.2는 `parse_dom`을 "capture 전략 구현의 기반으로 보존"(`05:319`)한다고 하지만, 파싱 결과를 **어디에 저장할지**는 어느 모듈도 맡지 않는다. `runner`가 `summarize_handoff`로 요약(`tools/__init__.py:75`)하긴 하나 그 또한 저장 책임이 아니다. R4의 "저장" 절반이 고아 상태다.

[권고] 저장 책임을 capture 하위(`DomCaptureStrategy`가 구조화 JSON을 어디에 보관하는가) 또는 신규 `store` 모듈로 명시하라. "추출은 있으나 저장 주체 없음"은 R4 요구사항의 절반 누락이며, 재작성 시 동일 오류(추출만 하고 저장 방치)가 반복될 수 있다.

### O4 — 이중 사용자(인간/에이전트) 충돌·동시성·권한 경계 미정의

[사실] 05 §1.1 정의 2는 이중 사용자 모델(인간 핸드오프 ↔ 에이전트 CDP 제어)을 규정하나(`05:56-58`), 두 주체가 **동일 탭/세션을 동시에 제어할 때의 arbiter(중재자)·락·우선순위**는 정의하지 않는다. `cdp_bridge.py`는 `contexts[0]`/`pages[0]`을 재사용(`cdp_bridge.py:62-66`)하므로 인간과 에이전트가 같은 탭을 두고 충돌할 여지가 있다.

[반대증거] 05 §2.1은 "인간이 이미 켜둔 헤드풀 크롬 세션을 에이전트가 이어받는다"(`05:100`)고 하지만, "이어받은 뒤 인간이 다시 개입하면?"이라는 역방향 핸드오프(HITL 복귀) 경계는 §6의 HITL이 수신만 다룰 뿐, 제어권 회수 주체를 정의하지 않는다.

[권고] §1.1 또는 §2에 "동시 제어 경계"를 추가하라(예: 인간 포그라운드 조작 시 에이전트 일시정지, 또는 세션 분리). 이 경계 부재는 협업 도구의 본질적 요구이나 05에서 빠졌다.

## 3. 기존 코드와의 불일치 (Code Inconsistencies) — 실증

### K1 — `constraints` 타입 불일치: JS 배열 전송 vs Python `str` (핵심 경로 붕괴 위험)

[사실] `src/extension/content_script/content_script.js:37`은 `function sendHandoff(intent = '', constraints = [])`로 기본값을 **배열**로 두고, `:43`에서 `constraints, // §3 스키마: string[]`로 주석과 함께 **배열**을 전송한다. 반면 Python `Handoff` 모델은 `constraints: str = ""`(`handoff.py:42`)로 **문자열**을 요구한다. `background.js`도 `:48-54`에서 CS로부터 받은 `constraints`를 그대로 포워드하므로 배열이 그대로 10899로 전달된다.

[사실 — 실행 실증] 본 리뷰가 pydantic v2로 `Handoff.model_validate({'constraints': []})`를 돌린 결과 `ValidationError`("Input should be a valid string")가 발생했다. 즉 content_script가 실제로 보내는 `constraints: []`는 `bridge_server.py:95`의 `Handoff.model_validate()`를 **통과하지 못해 400을 반환**한다.

[반대증거] 05는 `handoff.py`의 `constraints`를 `str`로 확정한 사유를 스스로 적고(`handoff.py` docstring `:10-11`), bridge_server가 `{"status":"ok"}`를 수신했다고 인용(`05:167`, `06_e2e_result.md` §5)하나, **그 E2E는 content_script의 실제 페이로드(배열)가 아닌 조작된 JSON이었을 가능성이 높다.** 핸드오프 본경로(익스텐션→10899)는 현재 계약 불일치로 동작하지 않는다. `handoff.py` docstring조차 "원본 초안에서는 string 배열이었으나 str로 확정"(`handoff.py:10-11`)이라 과거 배열 스키마에서 Python만 바뀌고 JS는 미갱신된 흔적이다.

[권고] 재작성 전이라도 **즉시 수정**하라: content_script.js `constraints`를 문자열로 직렬화하거나, `Handoff.constraints`를 `list[str]`로 되돌리고 핸드오프 소비처를 맞추라. 계약 bug를 05가 "개념 기준서"임에도 지적하지 않은 것은 중대한 누락이다.

### K2 — bridge_server PORT "고정" 불일치 (05 `[사실]` 오기)

[사실] 05 §3.2.3은 **"`HOST=127.0.0.1`, `PORT=10899` 고정"**(`bridge_server.py:32-35`)이라고 `[사실]`로 단정한다(`05:167`). 실제 코드는 `PORT: int = int(os.environ.get("BRIDGE_PORT", "10899"))`(`bridge_server.py:32`)로 **`BRIDGE_PORT` 환경변수로 오버라이드 가능**하며, 고정이 아니다. HOST만 `127.0.0.1`로 고정(`bridge_server.py:35`)이다.

[권고] 05의 `[사실]` 표기를 "`PORT=10899`(기본값, `BRIDGE_PORT`로 오버라이드 가능)"로 정정하라. `[사실]`은 실증 항목이므로 오기 자체가 컨벤션 위반이다.

### K3 — `bridge_server.py:25-26` "지연 import" 불일치 (05 오인용 + 모듈 docstring 오기)

[사실] 05 §3.3은 **"순환 import는 기존처럼 지연 import(`runner/__init__.py:80-81`, `bridge_server.py:25-26`)로 우회하지 말고"**(`05:182`)라고 쓴다. `runner/__init__.py:80-81`은 `run()` 내부의 지연 import(`from core.cdp_bridge import CDPBridge`)로 맞다. **그러나 `bridge_server.py:25-26`은 최상단 import**다(`from core.handoff import ...` / `from core.orchestrator import Orchestrator`). 지연 import가 아니다.

[반대증거] `bridge_server.py` 모듈 docstring `:10`조차 "Orchestrator 는 지연 import(lazy import)"라고 주장하지만 실제 코드는 최상단 import다. 05는 이 잘못된 docstring을 그대로 인용했다. 또한 docstring `:11`은 "Orchestrator 는 지연 import로 core↔agent 순환 import 를 방지한다"고 하지만, 실제로는 bridge_server→orchestrator→runner/cdp_bridge 방향의 단방향 import이며 순환 자체가 성립하지 않는다.

[권고] §3.3 인용을 `bridge_server.py` 항목에서 삭제(또는 ":26 최상단 import"로 정정)하고, bridge_server docstring 오기도 같이 바로잡으라.

### K4 — cdp_bridge "page.goto + 지터" 라인 오인용

[사실] 05 §3.2.4는 **"`page.goto` + 지터(`cdp_bridge.py:50-66`)"**(`05:171`)라고 인용한다. 실제로 `cdp_bridge.py:50-66`은 `connect()` 메서드(attach) 범위고, `page.goto`는 `:82`, 지터(`time.sleep(random.uniform(0.2,1.2))`)는 `:84`(모두 `control()` 메서드 `:68-89` 내)에 있다. §1.1의 `:60` connect_over_cdp 인용은 정확하나, goto/jitter 인용은 틀렸다.

[권고] 인용 라인을 `cdp_bridge.py:82`(goto) / `:84`(jitter) / `control():68-89`로 정정하라.

### K5 — Playwright "테스트/검증용" 불일치 + 용어 혼선

[사실] 05 §3.2.4 `[권고]`는 **"현재 Playwright 의존성은 테스트/검증용(`04_user_manual.md` §사전준비 3)"**(`05:172`)이라고 한다. 그러나 실제 `cdp_bridge.py:57`은 `from playwright.sync_api import sync_playwright`를 **런타임 제어 수송**으로 사용한다(connect→`connect_over_cdp`→`page.goto`). 즉 Playwright는 테스트 보조가 아니라 **실제 control 구현체**다.

[사실] 게다가 `pyproject.toml`의 `dependencies = ["pydantic>=2", "python-dotenv"]`에 playwright가 **선언되지 않아**, 의존성 설치만으로는 control 경로가 `ImportError` 난다(현재 venv에만 설치됨). 05가 언급한 "테스트/검증용" 프레임과 배치된다.

[반대증거] 05 §3.2.4는 `Controller` 인터페이스 아래 "CDP 구현체 외에 Playwright 기반 구현체도 교체 가능"(`05:172`)이라고 하지만, **현재 유일한 control 구현체는 Playwright의 `connect_over_cdp`**다(순수 raw CDP 클라이언트는 없음). "CDP 구현체 vs Playwright 구현체"라는 이분법은 실제와 맞지 않는다. `cdp_bridge.py` docstring `:7`조차 "CDP bridge"라 칭하지만 내부는 Playwright다.

[권고] "Playwright는 테스트용" 문구를 삭제하고, "control 모듈은 Playwright(`connect_over_cdp`) 기반이며 이를 `Controller` 구현체로 둔다"고 정정하라. 필요시 pyproject에 `playwright`를 핵심 의존성으로 추가하라.

### K6 — Orchestrator 삭제/축소(§5.3) vs bridge_server 보존(§5.2) 충돌

[사실] 05 §5.2는 `bridge_server.py`를 "구현체로 보존"한다(`05:282`). 그러나 `bridge_server.py:26`은 `from core.orchestrator import Orchestrator`를 최상단 import하고, `:96`은 `Orchestrator().receive_handoff(handoff)`, `:101`은 `Orchestrator().receive_hitl(hitl)`로 **Orchestrator에 하드 의존**한다.

[반대증거] 05 §5.3은 `core/orchestrator/__init__.py`의 runner 위임 흐름을 **"외부 에이전트가 CDP/bridge를 직접 쓰므로 오케스트레이션은 최소화하거나 제거"**(`05:292`)한다. §5.5도 orchestrator를 "재해석/축소"로 매핑한다. 그러면 bridge_server(보존 대상)가 의존하는 Orchestrator가 사라져 **보존 불가능**해진다. 05 §5.2와 §5.3이 서로를 깨뜨린다. 더욱이 §5.5 마이그레이션 표는 bridge_server→HandoffReceiver "보존(구현체)"로 적고 orchestrator→"재해석/축소"로 적어, 두 행의 의존 관계를 간과했다.

[권고] 재작성 범위를 정합하게 고쳐라: (a) bridge_server를 보존하려면 Orchestrator 의존을 `HandoffReceiver` 인터페이스로 흡수하거나, (b) Orchestrator를 제거하려면 bridge_server도 같이 재작성 대상으로 편입. "보존 + 삭제" 병기는 불가능하다.

### K7 (부가) — `HandoffReceiver` 인터페이스 과소명세

[사실] 05 §3.4의 `HandoffReceiver`는 `receive(payload)->Handoff` / `subscribe(agent)`만 정의한다(`05:202-204`). 실제 `bridge_server.py`는 검증 후 **`Orchestrator` 위임**까지 수행한다(`:96,:101`). 05가 "보존"한다는 컴포넌트의 실제 동작이 인터페이스 명세보다 크다.

[권고] `HandoffReceiver`에 위임 대상(큐/에이전트/오케스트레이터) 전달 책임을 명시하거나, bridge_server를 인터페이스에 맞춰 축소하라.

### K8 (종합) — 05가 코드를 어떻게 오독했는가 (synthesis)

[사실] K1~K7을 종합하면 05의 코드 인용은 두 가지 패턴으로 오독된다. (1) **라인/동작 오인용**: K2(PORT 고정 아님), K3(지연 import 아님), K4(goto 라인). (2) **의존성/경계 오독**: K5(Playwright 테스트용 아님), K6(Orchestrator 삭제 시 bridge_server 붕괴), K1(JS/Python 계약 불일치 미포착). 이는 05가 "기존 01~04 리포트"를 증거로 삼으면서 **실제 `src/`를 충분히 로드하지 않고** 이전 리포트의 서술을 그대로 계승한 결과로 보인다(§0.1이 경고한 "문서 자체 버전 덮어쓰기/오개념 정정" 패턴의 반복).

[권고] 05 차기 버전은 모든 `[사실]` 코드 인용을 `src/` 직접 로드로 재검증하라. 리뷰어 입장에서 05의 `[사실]` 신뢰도는 K1~K7 발견으로 인해 "재작성 전 재확인 필요"로 하향 평가된다.

## 5. 결론 — 05는 재작성 기준으로 충분한가?

[사실] 05는 리부트 방지 의도(§0.1), 정체성 3원칙, 쟁점 A/B 확정, 5인터페이스 모듈 경계, 재작성 범위를 갖춘 **유용한 최상위 기준서 초안**이다. 그러나 본 리뷰가 발굴한 **모순 4건(C1~C4), 누락 4건(O1~O4), 코드 불일치 8건(K1~K8)** 중 다수가 재작성 설계에 직접 영향을 준다.

[반대증거] 특히 **K1(`constraints` 계약 bug)**은 05가 "개념 기준서"임에도 현재 핸드오프 본경로(익스텐션→10899)가 pydantic 검증 실패로 동작하지 않음을 지적하지 못했고, **K6(Orchestrator 삭제 vs bridge_server 보존 충돌)**은 재작성 범위 자체가 내부 모순이다. **C1(서버 모호성)·O2(R5 누락)·O4(이중사용자 충돌경계)**는 "개념 정립 부재 → 리부트"라는 05의 핵심 경고(§0.1)가 정작 자기 문서에서 반복되는 지점이다.

[권고] **05는 재작성 기준으로 '충분하지 않다'**. 다음을 수정(버전 bump)한 뒤 설계로 내려가라.

### 5.1 수정 필요 항목 리스트 (우선순위 순)

| # | 구분 | 항목 | 수정 내용 | 심각도 |
|---|---|---|---|---|

## 5.4 05의 긍정 측면 (균형 평가)

[사실] 비판 리뷰이나, 05가 잘한 지점을 명시하지 않으면 수정 우선순위 판단이 왜곡된다. Analyst로서 다음은 긍정 평가한다.

1. **쟁점 A/B의 명시적 확정(§2):** DOM 1순위·스크린샷 폴백, 세션 공유 주경로를 "이미 결론 난 사안"으로 못 박은 것은 리부트 방지에 효과적이다. 이 결론은 `IDEA.md` 요구사항과 정합하며 재작성 설계의 안전 기반이 된다.
2. **정의 3 "도구는 뇌 없음" 명확화(§1.1):** 기존 `runner`/`llm`의 "내장 LLM" 오개념을 `[반대증거]`로 드러내고 `agent_iface`로 재해석한 것은 정체성 경계 확립에 기여한다.
3. **5인터페이스 모듈 경계 + 단방향 의존 원칙(§3.1~§3.3):** 재작성 설계의 골격으로 우수하다. 특히 §3.3 의존 방향(agent_iface → bridge/capture → control/session)은 순환 import 근절 설계로 타당하다.
4. **개방질문에 권고안 병기(§6.5):** 결론을 회피하지 않고 각 선택지 장단점을 정리한 점은 검토 팀 의사결정을 돕는다.

[권고] 긍정 지점(1~4)은 v2.1에서 보존하되, 본 리뷰 지적(K1~K8·C1~C4·O1~O4)을 같은 버전에 흡수하여 "좋은 초안"을 "신뢰 가능한 준거"로 격상하라. 특히 긍정 지점 3(모듈 경계)이 K6(Orchestrator 충돌)로 인해 실제로는 성립 불가 상태이므로, 경계 설계와 재작성 범위(§5)를 함께 정합시켜야 한다.
