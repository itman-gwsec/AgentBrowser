- **버전:** v1.0 (리스크 리뷰 — 단일 산출물)
- **검토 대상:** `docs/reports/05_concept_redefinition.md` (v2.0, 411행)
- **작성 역할:** AgentForge Risk-Assessor (R00 인용가능 evidence 기반 / R01 출처명시·반대증거동시보고 / R03 검증가능단위분해)

## 0. 검토 방법 및 한계

[사실] 본 리뷰는 05를 `read_file`로 전수 로드(411행)하여 분석했다. 리스크 판정의 1차 근거는 05가 인용한 소스/리포트 라인(`cdp_bridge.py:60`, `bridge_server.py:32-35`, `launcher.py:62-76`, `03_final_report.md`, `04_user_manual.md`, `06_e2e_result.md`)이며, 교차검증은 `06_concept_review_analyst.md`(v1.0)의 실증 사실(Handoff 검증 실패·playwright 미선언 등)을 인용했다.

[권고] 난이도/리스크는 "상/중/하" 3단으로만 표기한다. "상"은 통제 항목 선행 없이 진행 시 재작성 지연·보안 노출 가능성인, "하"는 기존 동작(partial) 재활용으로 낮음을 뜻한다. 정보 부족 지점은 "판단보류"로 표기.

[반대증거] 05 §6.4는 **실제 CDP 탭 제어가 한 번도 성공한 적 없음**을 명시적 한계로 보고(`05:348`). 즉 "현실성 상"으로 분류한 항목 중 세션공유·CDP제어는 아직 런타임 실증이 없어, 난이도는 설계 정합성이 아닌 "검증 공백" 기준으로 평가한다.

[권고] 본 리뷰는 Risk 역할이므로 "구현 얼마 걸리나"보다 "무엇이 터질 수 있는가"에 가중을 둔다. 각 항목은 심각도와 선행 통제를 1:1로 매핑한다.

## 1. 현실성 평가 (Feasibility) — 난이도 분류

### 1.1 이중 사용자 모델 (Human + Agent 동시 공유) — 난이도: 상

[사실] 05 §1.1 정의 2는 인간(익스텐션 UI)과 에이전트(CDP/Playwright)가 동일 세션을 공유한다고 규정(`05:56-58`). §2.1은 인간 로그인 프로파일을 에이전트가 이어받는 주경로를 확정(`05:102`).

[권고] 동일 탭에 인간 입력과 CDP 제어가 동시 작용하면 네비게이션 충돌·포커스 탈취·스크롤 위치 경합이 발생한다. 핸드오프를 "인간→에이전트" 일방 전달(`handoff.py:21-49`)로만 규정(`05:64`)하면, "동시 공유" 정의 2와 모순 구간이 남는다. 실현 가능하나 **충돌 조정 프로토콜(인간 입력 정지/재개 신호, 제어권 소유자 명시)이 선행되어야 한다** → 난이도 상.

[반대증거] 기존 `runner.run()`은 단독 제어만 가정(`runner/__init__.py:45-91`), 동시성 설계는 부재. 05도 이 충돌 해소책을 개방질문으로 남기지 않았다(설계 공백).

### 1.2 세션 공유 (CDP attach to 실제 Chrome) — 난이도: 중

[사실] `launcher.py:62-76`이 `--user-data-dir=profiles/<name> --remote-debugging-port=9222`로 실제 Chrome을 기동하고, `cdp_bridge.py:60`이 `connect_over_cdp("http://127.0.0.1:9222")`로 attach하는 경로는 E2E에서 Chrome 기동(PID 9430)·CDP 응답 성공까지 부분 검증됨(`06_e2e_result.md` §1, `03_final_report.md` §3.1.1).

[권고] attach 자체는 기존 산출물 재활용으로 실현 가능(난이도 중). 단 전제: 인간이 launcher로 debugging port 기동한 브라우저를 먼저 켜야 함. 이 "기동 순서 의존성"을 05가 강제하지 않으면 에이전트 진입 실패.

[반대증거] §6.4에 따르면 attach 이후 **실제 탭 조작(page.goto/클릭)은 미검증**(`05:348`). 연결은 되나 제어 효과는 미입증 → 현실성은 "연결까지 중, 제어까지는 미확정"으로 분리 평가.

### 1.3 CDP 폴백 (DOM 실패 시 스크린샷) — 난이도: 중

[사실] 05 정보경로 3은 DOM 파싱 불가 시 스크린샷(PNG) 캡처→외부 비전 위임을 규정(`05:116-119`). 스크린샷은 CDP `Page.captureScreenshot`로 획득 가능(`03_final_report.md` §4.2 경로 활용).

[권고] 캡처 채널은 이미 존재. 미해결은 "DOM 실패 판단 주체"(Q2)뿐 → 난이도 중. 단 외부 비전 에이전트가 PNG를 가져가는 전송 채널(CDP 직통 vs bridge)이 미정의되어 있어 그 연결부만 추가 설계 필요.

### 1.4 클립보드 텍스트 추출 — 난이도: 중(하)

[사실] 05 정보경로 4는 인간 Cmd+A/C 복사본을 OS 클립보드에서 도구가 읽어 추출한다고 규정(`05:123-125`). 이 경로는 `IDEA.md`에 없고 사용자 확정 방향으로 신규 편입(`05:125`).

[권고] macOS에서 Python 클립보드 읽기는 `pbcopy/pbpaste` 또는 pyobjc/TCC 권한으로 가능(난이도 중하). 단 **OS 권한 승인(TCC) 동의 절차**가 최초 1회 필요하고, 승인 거부 시 경로 차단 → 05는 이 권한 획득 단계를 명시하지 않음(설계 공백, 난이도를 하에서 중으로 격상).

### 1.5 플랫폼 종속 (macOS 하드코딩) — 난이도: 중

[사실] 05 §3.2.1 반대증거는 `launcher.py:24`가 macOS Chrome 경로를 하드코딩하여 Linux/Windows 기동 불가를 명시(`05:159`). `04_user_manual.md` 주의사항 4도 macOS 전용을 경고.

[권고] MVP가 macOS 단일이라도 `SessionManager`를 OS별 전략으로 분리(`05:159` 권고)하지 않으면, 추후 타 플랫폼 이행 시 재작성 전체가 흔들린다. 비목표이나 "확장 대비" 분리만은 재작성 초기(§5.1 단계 1)에 인터페이스로 잡아두라.

## 2. 리스크 평가 (Risk) — 심각도 분류

### 2.1 보안 — 프로파일 격리 — 심각도: 상

[사실] 주경로는 인간이 실제 로그인한 프로파일(`profiles/<name>`)을 이어받음(`05:102-104`). 이 프로파일엔 쿠키·세션토큰·인증 상태가 포함된다. `04_user_manual.md` 주의사항 3은 정리 유틸 부재를, `02` §10은 권한 700 미적용 상태를 보고(`05:343`).

[권고] 실제 로그인 프로파일을 에이전트(CDP)가 제어하면 **쿠키/토큰 유출·로그인 된 행위 가장** 경로가 열린다. 05 Q3(격리 수준)을 (c)격리+권한 700으로 조기 확정하고, `profiles/` 디렉터리 모드 700·타 사용자 비가독을 강제하라. 이 통제 없이 재작성 착수 시 인증 자격 노출 리스크 상.

[반대증거] 05 §1.1 정의 1은 "외부 서버 운영 안 함"을 선언하나(`05:51`), 동시에 `bridge_server.py`(10899 HTTP)를 보존(`05:167`) → "서버" 경계 모호(분석 리뷰 C1). 이 모호성은 보안 경계(무엇이 신뢰 경계인가)를 흐려 리스크 평가를 어렵게 한다.

### 2.2 보안 — 클립보드 민감정보 — 심각도: 중(상)

[사실] 05 정보경로 4는 클립보드 텍스트를 외부 에이전트에 전달(`05:124`). 클립보드엔 비밀번호·API 키·PII가 일시 체류할 수 있다.

[권고] 클립보드 읽기는 **최소 권한+선택적 수집**으로 제한하라. 전체 클립보드 무조건 전송이 아닌, 인간이 명시 플래그로 "이 복사본 전송" 동의한 경우만 전송하는 게이트를 둘 것. 이 통제 부재 시 민감정보 외부 유출 경로 = 심각도 상으로 상승.

### 2.3 봇 탐지 회피 실효성 — 심각도: 중

[사실] 05는 실제 Chrome 세션 공유를 봇 탐지 회피 "최상"으로 규정(`05:105`). `IDEA.md` §3 R2도 헤드풀+인간유사동작으로 완화 명시.

[반대증거] CDP attach 자체가 탐지 시그널이다. `navigator.webdriver` 플래그, CDP 런타임 이벤트, 자동화专属 TLS/클라이언트 지문은 실제 세션 공유만으로 소거되지 않는다. `03_final_report.md` §1.4는 현재 지터(time.sleep)만 적용, 베지어 궤적은 미구현(`05:106`). 즉 **회피 실효성은 "부분 완화" 수준이며 "탐지 불가"가 아님** → 과신 금지.

[권고] 회피를 "최상"이 아닌 "부분 완화"로 재기술하고, 05 §2.1의 "최상" 표현을 완화하라. 지터 외 베지어 궤적·타이핑 리듬 주입을 capture/control 표준 기능으로 격상하되, 탐지 우회 보장은 하지 말 것.

### 2.4 인간+에이전트 동시 충돌 — 심각도: 중(상)

[사실] §1.1 정의 2의 "동시 공유"와 §2.1 주경로가 동시 활성을 전제(`05:56-58,102`). 제어권 소유자 전환 규칙은 미정의.

[권고] 충돌은 데이터 오염(에이전트가 인간 입력 중 페이지 이탈)·의도 불일치(양쪽이 다른 URL로 이동)를 낳는다. §1.1에 **제어권 소유자 상태머신(Idle/Human/Agent)**과 핸드오프 수락/반납 명시를 추가하라. 이 누락은 런타임 장애 빈도 상으로 직결.

[반대증거] 05 핸드오프 스키마(`handoff.py:21-49`)는 intent/constraints만 담고, "수락 중인 인간 세션 상태" 필드가 없어 충돌 감지용 메타가 부재.

### 2.5 의존성 선언 불일치 — 심각도: 중

[사실] 분석 리뷰는 `playwright`가 `pyproject.toml`의 `dependencies=["pydantic>=2","python-dotenv"]`에 선언되지 않았음을 실증. 05 §3.2.4는 Playwright 기반 `Controller` 구현체 교체를 권고(`05:172`).

[권고] 재작성 중 Playwright 구현체를 실제로 쓰려면 의존성 선언 누락으로 런타임 import 실패. `pyproject.toml` 의존성 정합을 재작성 단계 1에서 먼저 교정하라. 선언부 불일치는 게이트(ruff/pytest)를 통과해도 배포 시 터진다.

### 2.6 MV3 익스텐션 수명/백그라운드 종료 — 심각도: 중

[사실] 05 §3.2.2·§3.2.3은 CS/BG를 capture/bridge로 보존(`05:163,167`). `IDEA.md` §6은 MV3 제약을 명시. 분석 리뷰는 MV3 백그라운드 수명 보완 설계가 기존에 재현된 적 있음을 지적(`05:360` 인용).

[권고] MV3 서비스 워커는 일정 시간 비활성 시 종료되어, 장시간 대기 핸드오프 수신(10899)이 누락될 수 있다. `bridge` 모듈 보존 시 활성 유지 메커니즘(주기 ping/이벤트 기반 깨우기)을 명시하지 않으면 수신 신뢰도 하락. 이는 §4.3 게이트로 잡히지 않는 런타임 리스크다.

### 2.7 감사/추적 부재 (Audit Trail) — 심각도: 중(하)

[사실] 05는 에이전트가 CDP로 실제 세션을 조작(쿠키/로그인 행위 가장 가능, §2.1)하는 주경로를 확정(`05:102`)하나, 조작 이력을 기록하는 감사 로그 설계는 없다. 핸드오프 스키마(`handoff.py:21-49`)도 intent/constraints/timestamp만 보관.

[권고] 외부 에이전트가 인간 계정으로 행위하는 구조에서는 "무엇을 했는가" 추적이 사고 대응·책임 소재 파악에 필수다. `control`/`agent_iface` 계층에 조작 감사 로그(액션·타겟·타임스탬프·소유자)를 표준 기능으로 두라. 누락 시 보안 사고 발생 시 원인 특정 불가 = 심각도 중상으로 격상 여지.

[반대증거] 정의 3(도구는 뇌 없음, `05:62`) 때문에 "로깅은 외부 에이전트 책임"으로 치부될 수 있으나, 도구가 수행한 제어 자체는 도구 레벨 기록이 자연스럽다. 경계를 명시하지 않으면 양쪽 모두 "남의 책임"으로 방치.

## 3. 구현가능성 (Implementability)

### 3.1 방식 2 (완전 재작성) 공수 — 난이도: 상

[사실] 05 §5.1은 `src/` 전면 재작성 원칙(`05:270`), 기존 테스트 13건은 새 설계(§3) 반영 후 재작성(`05:271`), §5.4 완료기준은 5 인터페이스 구현+TDD+ruff/pytest/pydantic/mypy 게이트(`05:296-300`).

[권고] 공수는 상. 단 05가 §3에 5 인터페이스 시그니처를 의사코드로 이미 제공(`05:188-223`)하여 설계 불확실성이 낮다 → 이는 리부트 방지에 유리. 리스크는 "공수 과다→중간 포기→재시작" 패턴 재현. 이를 막으려면 §5.1 재작성 순서((1)인터페이스→(2)TDD→(3)결선→(4)게이트)를 엄격히 단계별 게이트로 잘라야 한다.

[반대증거] 분석 리뷰는 `Handoff.model_validate({'constraints': []})`가 pydantic v2 검증 실패, `playwright`가 미선언임을 실증. 즉 재작성 시 의존성 선언·스키마 정합부터 누락 발견 → 보존 대상(`handoff.py`)도 blind 이관 불가, 재검증 필수.

### 3.2 OOP 모듈 경계 — 응집도/결합도 — 난이도: 중

[사실] 05 §3.1은 5 모듈(session/capture/bridge/control/agent_iface)을 인터페이스 중심으로 분리(`05:146-153`), §3.3은 단방향 의존(`agent_iface→bridge/capture→control/session`)을 의무화(`05:182`).

[권고] 응집도는 양호(책임 분리 명확). 결합도는 §3.3 주입 원칙으로 낮출 수 있으나, **`agent_iface`가 외부 에이전트 연결점인데 그 경계가 Q1(직접 vs 중개) 미결이라 모호** → 인터페이스 `AgentController` 시그니처(`05:216-222`)가 실제로 누구를 바인딩하는지 불분명. Q1 확정 전까지 `agent_iface` 결합도는 평가보류.

[반대증거] §3.2.3이 `bridge_server.py`(HTTP)를 보존하며, 이는 정의 1 "서버 운영 안 함"과 충돌 가능(분석 C1). 모듈 경계가 "로컬 HTTP 리스너 허용 여부"를 못 박지 않아, `bridge` 모듈의 신뢰 경계가 흔들린다.

### 3.3 테스트 재작성 공수 — 난이도: 중(상)

[사실] 05 §5.1은 기존 13건 테스트(unit 10+integration 3)를 "이전 밀결합 설계에 종속"이라 버리고 재작성(`05:271`). §4.3은 TDD(실패 테스트 먼저)+ruff 클린+mypy strict 권고(`05:250-251`).

[권고] TDD로 새 인터페이스 5종×구현체를 모두 커버하려면 테스트 공수 자체가 상급. mypy strict는 `03_final_report.md` §6.8에서조차 별도 확인 권고로 남긴 미검증 항목. 재작성 일정 산정 시 mypy strict 풀패스 여유를 누락하지 말라(게이트 포함 시 공수 상승).

### 3.4 보존 대상 경계 리스크 (§5.2) — 난이도: 중

[사실] 05 §5.2는 기존 4개(익스텐션 CS/BG·`launcher.py`·`bridge_server.py`·`cdp_bridge.py`)를 "동작하는 부분"으로 보존(`05:278-283`). §5.5는 이들을 §3 인터페이스로 매핑(`05:306-316`).

[권고] 보존 판정은 "E2E 부분 검증"에 근거하나, §3 인터페이스 시그니처(`05:188-223`)와 기존 코드가 실제로 1:1 정합하는지는 분석 리뷰가 지적한 불일치(`bridge_server.py` 미검증 스키마, `runner` 밀결합)로 보아 보증되지 않는다. 보존을 "그대로 이관"이 아니라 "인터페이스 계약 충족 여부 재검증 후 이관"으로 절차화하라.

[반대증거] §5.2 표는 `runner.run()` CDP 직접 호출만 제외(`05:285`)하고, `bridge_server.py:82-111`의 POST 분기/`background.js:15-35` fetch 전송이 새 `HandoffReceiver`/`AgentController` 경계와 정합하는지는 미검증. 보존 선언이 조기 확정되면 경계 위반 코드가 그대로 이월.

## 4. 개방질문 Q1~Q4에 대한 Risk 입장

### 4.1 Q1 (에이전트 연결: 직접 vs 중개) — Risk: (c)병존 + 보안 제약

[사실] 현재 CDP 직접(9222)과 Python 중개(10899) 경로 혼재(`05:329`). 05 §6.5는 (c)병존을 권고안(`05:362`).

[권고] Risk도 (c)병존에 동의하나 **강제 제약** 추가: 9222 바인딩은 `127.0.0.1` 외 노출 절대 금지(원격 노출 시 RCE 경로). 10899는 핸드오프 수신 전용 경계 고정. 이 바인딩 제약을 05에 명문화하지 않으면 (c)병존은 공격면 확대.

### 4.2 Q2 (폴백 판단 주체) — Risk: (c)익스텐션 플래그 + 에이전트 결정

[사실] 기존 CS/BG는 DOM 캡처만 하고 폴백 판단 로직 없음(`05:335`). §2.3은 "DOM 실패 시 스크린샷"만 규정(`05:116`).

[권고] (c)익스텐션이 "파싱 가능 여부" 플래그만 달고 에이전트가 결정하는 구조(05 §6.5 권고)에 동의. 단 **오판단 리스크**: DOM 파싱 가능인데 실제로는 구조화 실패인 경우가 있어, 플래그 신뢰도 임계치(예: 노드 수/텍스트 밀도)를 capture 계층에 둘 것을 권고. 잘못된 폴백은 외부 비전 왕복 낭비→비용 상.

### 4.3 Q3 (프로파일 격리) — Risk: (c)격리 + 권한 700 (강력 권고)

[사실] `profiles/<name>`은 별도 `user-data-dir`이나(`05:341`), 정리 유틸 부재·권한 700 미적용(`05:343`). 기본 시스템 크롬과는 비공유(사용자 지적).

[권고] Risk는 (c)를 **강력 권고**(05 §6.5 권고와 일치). 실제 로그인 프로파일이 타 사용자/프로세스 가독이면 인증 자격 노출 = §2.1 리스크와 직결. 다중 작업 격리 레지스트리(이름→경로·만료) 도입을 MVP 이후라도 최소 설계안에 두라.

### 4.4 Q4 (E2E 검증 책임) — Risk: (a)완료 게이트 포함 (강력 권고)

[사실] §5.4는 이미 E2E CDP 제어를 완료기준 3항에 포함(`05:299`). 그러나 §6.4는 이를 "미결"로 개방(`05:348`). 실제 탭 제어는 한 번도 성공 못 함(`05:348`).

[권고] (a)게이트 포함에 강력 동의(05 §6.5 권고). 미검증 상태로 "재작성 완료" 선언하면 §6.4 반대증거(런타임 미검증)가 그대로 재현 → 리부트 방지 원칙(§4) 위배. 외부/테스트 에이전트가 9222에 붙어 실제 `page.goto`/클릭을 수행하는 스모크를 게이트 스크립트로 구체화하라.

## 5. 결론 — 05 기준 재작성 착수 가능 여부

[사실] 05는 정체성 3원칙·정보경로 4갈래·OOP 5인터페이스·리부트 방지 절차를 갖추어 "최상위 준거"로서의 골격은 충족(`05:382-387`). 단 §6.4(런타임 미검증)·분석 C1(서버 경계 모호)·§2.1(회피 과신) 등 통제 공백이 존재.

[권고] **05 기준 재작성 착수는 가능하나, 다음 선행 조건(통제 항목)을 본 문서 버전 bump로 먼저 반영할 것을 권고한다.**
1. **정의 1 스코프 한정**(C1): "원격/클라우드 백엔드 금지, 로컬 루프백 브리지 10899는 예외"로 모호성 해소.
2. **Q3 격리 정책 확정**(c)+권한 700 강제, `profiles/` 비가독.
3. **Q4 게이트 포함 확정**(a)+실제 CDP 제어 스모크 스크립트화.
4. **보안 통제 명문화**: 9222 루프백 바인딩 강제, 클립보드 선택적 수집 게이트(§2.2).
5. **회피 실효성 재기술**(§2.1 "최상"→"부분 완화").
6. **동시충돌 제어권 상태머신**을 §1.1에 추가(§2.4).
7. **의존성 정합 선교정**(§2.5): playwright 등 `pyproject.toml` 누락 보완.
8. **MV3 백그라운드 수명 대응**(§2.6): bridge 활성 유지 메커니즘 명시.

[반대증거] 위 8개 중 하나라도 미반영된 채 재작성을 "방식 2 전면"으로 착수하면, §6.4 미검증·프로파일 격리 누락·서버 경계 혼선이 그대로 이월되어 리부트 재현 패턴(05 §0.1)이 반복될 여지가 남는다. 단 이는 "불가능"이 아니라 "통제 선행 필요" 수준이다.

[권고] 착수 절차: (1)본 리뷰 선행조건을 05 v2.1로 bump → (2)§5.1 순서대로 인터페이스 먼저 TDD → (3)각 완료게이트 통과. 이 순서가 05 §4.1 "개념 정립→설계→구현" 원칙과 정합하며 리부트를 실질 차단한다.

### 5.1 재작성 착수 단계별 게이트 체크포인트

[사실] §5의 8개 선행조건을 "언제" 반영할지 게이트와 매핑한 실행 순서. 각 게이트 통과 전 진행 금지(05 §4.3 원칙).

1. **게이트 G0 (문서 개정):** 조건1·5·6(정의1 스코프/C1, 회피 재기술, 제어권 상태머신)을 05 v2.1로 bump. — 미통과 시 설계 기준 모호.
2. **게이트 G1 (의존성/보안 선교정):** 조건4·7(9222 루프백 바인딩, pyproject 정합)을 재작성 단계1에서 먼저 교정. — 미통과 시 배포/RCE 리스크 상.
3. **게이트 G2 (격리 정책):** 조건2·3(Q3(c)+권한700, Q4(a) 스모크 스크립트화) 확정. — 미통과 시 프로파일 유출·런타임 미검증 잔존.
4. **게이트 G3 (인터페이스 TDD):** §3.1 5종 시그니처 구현체 + 단위테스트. 보존 대상(§3.4/R11)은 계약 재검증 후 이관.
5. **게이트 G4 (통합+런타임):** R10 스모크(실제 9222 붙어 page.goto/클릭) 통과 + R6 bridge 활성유지 검증. — 미통과 시 §6.4 반대증거 재현.
6. **게이트 G5 (품질):** ruff 0 errors / pytest 전부 passed / pydantic v2 / mypy strict(권고). R7 감사로그 존재 확인.

[권고] G0~G2는 "착수 전" 선행 통제(R1·R8·R10·R12 심각도 상 대응). G3~G5는 재작성 진행형 게이트. G0 미통과 상태로 G3로 건너뛰면 05 §4.1 위배 = 리부트 재현 여지.

### 5.2 본 리뷰의 범위 한계 (Role Boundary)

[사실] 본 문서는 Risk-Assessor 역할 한정 산출물이며, 05의 설계 타당성·코드 불일치 사실관계는 `06_concept_review_analyst.md`(분석 리뷰)가, 현실성/리스크/구현가능성은 본 문서가 담당한다. 두 리뷰는 상호 보완적이다.

[권고] Risk 판정의 "심각도 상" 항목(R1·R8·R10·R12)은 분석 리뷰의 실증 사실(C1 서버경계모호, Handoff 검증실패, playwright 미선언, §6.4 런타임 미검증)에 의존한다. 본 리뷰의 선행조건(§5)은 분석 리뷰 결론과 충돌하지 않으며, 05 v2.1 bump 시 양 리뷰의 지적을 통합 반영할 것을 권고한다.

[반대증거] 본 리뷰는 런타임 실행 실증을 수행하지 않았다(05 로드 기반 정합 분석 + 분석 리뷰 실증 인용). 따라서 "세션공유/동시충돌"의 실제 발생 빈도는 판단보류이며, G4 런타임 스모크로만 확정 가능하다.
